# P0 COMBAT RELIABILITY — GHOST HITS AND MISSING BITES

**26 November 2026 · Preparation only; no gameplay changes made.** This addendum is mandatory for the FERAL full-hub perfection preparation (PR #14). It responds to two current user-reported defects:

1. **Ghost hit:** a bite sound, impact, animation or visible candidate occurs but the target's health does not decrease / no server-accepted damage can be established.
2. **Bite does not register or initiate:** the user's bite input does not produce a normal attack marker or eligible, server-accepted hit, even when apparently close to a target.

These are **separate P0 functional defects**, not a request for another HUD cue, debug counter or sound change. They block a claim that the combat system is perfected.

## Source-grounded starting facts (v2412 client capture)

- **Input and preemption:** \`renaissance/src/controller.luau\` \`h:preInput\` handles MouseButton1/ButtonR2, releases owned automatic Rest, cancels feeding, records a transaction and passes a possible post-Rest action to \`combat_input.luau\`.
- **Post-Rest bite:** \`combat_input.luau\` schedules one delayed \`bridge:tryNativeBite(now)\` after the captured Rest stand-up lock; this only occurs if native callback discovery succeeds. A Lua \`pcall\` succeeding does **not** mean the native attack, hit claim or damage was accepted.
- **Actual native gates:** \`roblox.luau\` \`biteReadiness\` has restrictions for Rest and the native stand-up lock (often ~0.7 seconds), native cooldown, carry/pin/feeding/ability states, venom/recoil and server time. Native callback discovery may be VM-isolated or the captured upvalues may differ after an update.
- **Target geometry:** \`roblox.luau\` computes a client-side body gap/angle/vertical threshold and a separate target cue/assist. The displayed 15px marker and extended-only client geometry do not prove the game's native or server-side hit test accepted a target. Same-tree and occlusion shortcuts require validation.
- **Observed feedback:** \`controller.luau\` records \`WolfBiteAt\`, \`FeralBiteLocal\`, a native \`FeralHit\` event and short-window target Humanoid health. It may classify a generic latest transaction using a feedback target that differs from the current guide; target HP sampling is fallible when the target isn't in the earlier candidate list, health changes late, the target regenerates or another attacker is involved.
- **Existing prior research:** \`docs/FEATURE_AUDIT.md\` records that \`FeralCombatClient\` may present a local impact before \`FeralHit\`, that the post-Rest lock can stop the first bite, and that earlier guide ranking differed from native target selection. It does **not** establish that every ghost hit is generated by the hub.

## The causal bite pipeline to reconstruct

\`Physical attack input\` → \`native controller accepts click\` → \`rest/cooldown/ability checks pass\` → \`WolfBiteAt/attack animation\` → \`native selection of actual target\` → \`outbound bite claim as performed by the game's own code\` → \`native game hit reply\` → \`replicated target health change\`.

**Keep these distinct categories:** NO_INPUT; INPUT_CONSUMED_BY_UI_OR_MINIGAME; NATIVE_GATE_REST; NATIVE_GATE_COOLDOWN; NATIVE_GATE_ABILITY/CAPTURE/FEED; NATIVE_CALLBACK_UNAVAILABLE; ATTACK_MARKER_ONLY; TARGET_CLAIM_UNKNOWN; TARGET_MISMATCH; LOCAL_IMPACT_ONLY; SERVER_REPLY_PROTECTED; SERVER_REPLY_NO_DAMAGE; SERVER_REPLY_DAMAGE_WITHOUT_CORRELATED_HP; HP_DECLINE_NO_CONFIRMED_AUTHORSHIP; and CONFIRMED_CORRELATED_RESULT. No event is promoted to a higher assurance category merely because the animation/sound played.

### Hypotheses to test, not conclusions

**C01 — First attack after Rest is lost.** The code releases Rest on input but native \`doBite\` may check the still-active stand-up lock; the single deferred retry cannot work if callback discovery is unavailable, if the native attack ended/cooldown changed, or if it fires after the opportunity has passed. Compare first bite after 0, 100, 300, 700, 1000 ms since the last owned Rest signal against a no-Rest control. Separate native Rest lock from client \`WolfRest\` pose masking.

**C02 — The client attack is intercepted or not delivered.** InputBegan, ContextActionService priorities, native grab/minigame interception, combat input retry, feeding and UI click-area exclusion can alter which handler sees MouseButton1/ButtonR2. Reconstruct the original binding priority and session takeover path, then ensure ordinary manual attacks are not consumed by automation. Avoid duplicate synthetic clicks.

**C03 — Geometry disagrees with the actual hit test.** Client-side extended reach, body-gap approximations, vertical allowances, camera/movement direction and same-tree shortcuts can produce false-positive cues. Compare actual native closest-body score, native candidate and occlusion with displayed guide; do not interpret extended-only cue as accepted range.

**C04 — Moving target and network timing.** Client snapshot may be ahead of the authoritative target's position. Log local target velocity and root/body positions at the bite marker and at the game's reply, with game clock uncertainty, rather than treating the instant a sound plays as the impact time.

**C05 — Wrong target associated with a bite.** A late \`FeralHit\` reply or \`FeralBiteLocal\` may overwrite the target in the latest unmatched transaction. Tie observations to compatible character generation, native target, time window and source action; ambiguous concurrent hits remain unattributed.

**C06 — Damage accepted but not visible in the chosen window.** The selected target may not be in the 45-stud cached pre-bite list; target health can update later, recover, grow or be changed by other players. Keep immutable baseline per candidate and re-evaluate at a bounded delayed interval, with same-MaxHealth and observed-target identity checks.

**C07 — Game version/native rules changed.** Verify the live PlaceVersion, species and ability profile against captured v2412 before assuming old offsets and private closure shapes still match. A revised native handler or server acceptance rule cannot be repaired solely by local config edits.

**C08 — Automated hunting has a separate gap.** Territory hunting's \`amber_hunt\` and \`amber_bridge:bite\` use their own movement/attack interface and target projection. Its input, target alignment, target-feasibility and observed HP outcome must be checked against the same combat evidence contract; do not leave automated hunting “working” based on sound or a simulated HP drop.

## Functional upgrade tracks (future implementation)

### Track 1 — Native attack availability and first-bite correctness (P0-A)

- Explicitly reproduce lost bites after auto Rest, manual Rest, no Rest and while combat-tagged. Record click time, native gate state, \`WolfBiteAt\`, late marker, native reply and target HP separately.
- Move from a heuristic “native function call succeeded” state to a real native attack-transition acknowledgment. Never send arbitrary extra damage claims or pretend a callback invocation delivered a hit.
- Make the Rest-to-attack handoff atomic and reversible: cancel owned Rest before user bite, preserve genuine manual Rest, avoid re-arming during the entire native attack/cooldown, and leave one bounded opportunity for the original native bite path when it is legitimately available.
- The absence of private native callbacks must not cause the hub to swallow/consume the user's normal game input. Preserve actual native binding as the primary path and report any optional retry as PARTIAL.
- Validate feeding, capture, carry, flight, talon/dive, Hippo ability, venom recoil, climbed/tree and minigame states without unwanted cancellation.

### Track 2 — Real targeting / hit-geometry alignment (P0-B)

- Revisit captured native selection and hit scoring, and align the hub's visual/assistance candidate with the actual native selected target (or explicitly mark the visual-only cue unknown).
- Ground truth tests: head-on, side-on, rear, tiny body, large body, same-tree elevations, uneven terrain, moving target, crowded targets and target just beyond stock range.
- Correct stale geometry and target-switch flicker; prevent any client marker from stating “hit-ready” when native readiness, occlusion, protection or server range is unknown.
- Prefer a proven stock-native action with accurate feedback over enlarging local client geometry that produces false confidence or ghost hits. Avoid direct enemy part mutations, fabricated damage packets and client HP overlays.

### Track 3 — Ghost-hit elimination (P0-C)

- Distinguish normal bite sound/animation, visual local hit effect, actual native hit reply, protected/no-damage feedback and target replicated HP. They may not all occur for one bite.
- Group correlated evidence by animal generation, attack marker/session, native target identity and safe time window. Do not assign an arbitrary outgoing reply to an unrelated current guide or another player's damage.
- Improve target HP baselines: collect from actual eligible candidates *before* a native attack, track max HP stability, handle latency and respawns, keep bounded delayed post-attack reads, and mark ambiguous concurrent damage as unattributed.
- Where native accepted damage remains impossible due to authoritative range/armour/condition rules, report the exact restriction and optimise native movement/angle/timing instead. Masking a missing hit or faking the sound is not a fix.

### Track 4 — Combat + movement + ability integration (P0-D)

- Stable melee availability in standing, walking, sprinting, turning, on slopes, on trees, through permitted climb states and immediately after normal movement mode transitions.
- Attacks must not cause Vulture flight freeze or leave a Rest pose while moving; recovery must not block combat even while poison or injury clearance remains requested.
- Minigame automation must not steal MouseButton1 on ordinary fighting, substitute an unverified Perfect result, or discard a native bite session.
- Include a dedicated ground-vs-tree-vs-water target/reach mode table per supported species, with accurate fallback for unknown modes.

## Live comparison and exit criteria

1. Choose same species, growth, environment, game PlaceVersion and comparable target/HP conditions. Run the normal unmodified native game, the released 15.7.0 hub, and the new isolated candidate in paired trials.
2. For each attack, record actual input, chosen native target, marker, reply, safe/protection flag, target HP/MaxHealth before and after, ping/latency estimate and simultaneous actors. Do not infer damage solely from bite SFX or an animation.
3. Break down per-mode rates: percentage of eligible manual inputs reaching a native marker; percentage of markers receiving matching hit reply; percentage of matching replies correlated with health change; percentage of false-positive *claimed* hits. A hub change that merely removes a false label improves truthfulness but **does not** resolve missed native damage.
4. Put extra emphasis on ground close-range, moving prey, behind/side, same-tree vertical, high latency and 0–1.2 s after recovery exit.
5. Release gate: no new input or combat softlock, no duplicate bite claims, no misleading “damage landed” result; reproducible reduction in lost eligible bite attempts and unexplained ghost hits under matched live conditions. If the server rejects a client-only reach expansion, disable/limit that claim rather than saying it works.
6. All existing Renaissance and Territory regression suites stay green. Add direct unit/component/service-boundary tests for each root-cause repair and long session cleanup. Leave stable launchers untouched until review and live acceptance.
